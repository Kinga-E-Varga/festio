# Database — `src/db/` and `seed/`

The database: reads, writes, schemas, paths, and the emulators' seed. Part of `context/repo-map.md`.

Every page reads it (server only). The host's saves write it through `src/db/writes/`. Shapes: `context/features/pending/database.md`.

- `src/db/reads/` — the pages' reads, Admin SDK, each card checked by its schema, each loader in React `cache()` and behind `connection()` (nothing read at build). `session.ts` (`SESSION_COOKIE`, `loadHostId` — the signed-in uid or null, `requireHostId` — else to sign-in, `freshSignIn` — the token signed in within `FRESH_SIGN_IN_SECONDS`), `access.ts` (**the shared check**: `hostEvent` — one of the signed-in host's events or null, `openEvent` — not found, or Home once archived; `eventMetadata` — a host page's tab title; every host page and Server Action starts here), `host.ts` (`loadHost`, `loadHostLogin` — how they sign in, for the re-enter step), `events.ts` (`toDashboardEvent` — countdown and closes in worked out; `loadHostEvents`, `eventsOfHost` (the same without the session check, for a Server Action that made it), `eventIdBySlug` (the slug card alone, read once per page), `linkGone` (blocked because its event's data is deleted: "no longer available"), `loadEventBySlug` through it, its slug → event link cached by `memo` (the event card always fresh), `guestListCount`), `guests.ts` (`loadGuests`, once per event per request), `feed.ts` (no Next, so tests call it: `latestReplies` — a host's newest replies across events in one collection group query on `hostId`, or one event's; `feedTags` — their Unknown / Duplicate tags from their names' group only), `invitation.ts` (`loadInvitation` — read fresh, for the editors and print; `loadShownInvitation` — for the guest page and the Overview's preview, cached by `memo` on `invitationVersion`, and read only when the page shows it; `modularStart`), `activity.ts` (latest replies through `feed.ts`: `loadRecentReplies` the host's (the side panel's, through `loadLatestReplies` in `src/actions/host.ts`), `loadEventReplies` an Overview's, cached by `memo` on `dataVersion`; `newReplyCount` — guests' replies since `lastVisit`), `parse.ts` (`parseCard` / `parseCards`: a card failing its schema is logged and read as missing), `visitor.ts` (`visitorKey` — the visitor's IP, hashed), `unlock.ts` (`unlockCookie`, `isUnlocked` — this browser typed the current password), `dashboard.ts` (`loadHostSummary`: host, events, alerts — the dashboard's shell and Home, and the landing bar; not the latest replies, which load when their panel opens). Reads that take a `DashboardEvent` (`loadGuests`, `loadInvitation`, `guestListCount`) only get one a check returned.

- `src/db/writes/` — the saves, Admin SDK. They run without Next or React, so a script (step 8's nightly job) can call them. `save.ts` (`SaveError`, `SaveRefused`, `expectVersion` — the `version` check, `refusal` — a refused save as an `ActionResult`), `event.ts` (`ownEvent`, `readOwnEvent` — the same check outside a transaction, for an action that needs a field first, `writeEventSettings`, `writeCancel`, `writeReopen`, `writePrintSettings`), `slugs.ts` (claiming a link in a transaction, blocking the old one), `counts.ts` (**the one counter function**: `readCountInputs`, `countsOf`, `countsAfter` — after a save's change, `readNameGroup` — the cards that decide how some names count and are tagged, in a transaction (`inTransaction`) or not (`DIRECT`); `readReplyGroup` / `countsWithReply` — a guest's reply counts only the cards its names can change, `affectedKeys` / `readChangeGroup` / `countsWithChange` / `countsWithHostChange` — the same for a host's guest-list save (the changed names' group, closed over shared names and matched list names; a full recount past `GROUP_MAX_ROUNDS` / `GROUP_MAX_NAMES`), `repairCounts` — from the replies the guest list page loaded; the seed uses it too), `reply-ref.ts` (`replyRef` — every reply write goes through it, adding `nameKeys` / `listNameIds` and the event's `hostId`), `invitation.ts` (`writeInvitation` — raises `invitationVersion`), `guests.ts` (`writeGuestChanges`, `setGuestListOn` — the switch alone: no recount), `guest-reply.ts` (`writeGuestReply` — visibility, password, closing time, rate limit, cap, then the reply and counters in one transaction), `rate-limit.ts` (`rateLimits/` cards: `limitFor`, `readAttempts`, `countAttempt`, `unlockAttempt`), `delete-event.ts` (`deleteEventData` — a past or cancelled event's data, `leftoverEvent` — what the event card keeps).
- The event card's counters: `counts` holds both list settings (`shownCounts` picks), `summary` (ages, diets, answers of people coming), `dataVersion` (a reply or list-name save) and `invitationVersion` (an invitation save), for the `memo` caches (`src/lib/memo.ts`; no clearing, as several servers run).
- `src/db/schemas/` — one Zod schema per Firestore card (`event`, `invitation`, `reply`, `guest-list`, `user`, `slug`, `seating`, `payment`, `rate-limit`) plus `common`, and `guest-changes` (the guest list page's save, with its `GuestChanges` / `ReplyInput` types). Plain Zod, no Firebase import, so browser and server share them. The value lists (visibility, packages, age groups, diets, …) live here; `src/types/` derives its unions and `PrintSettings` / `AnswerValue` from them.
- `src/db/limits.ts` — `EVENT_KINDS`, `TITLE_MIN`/`MAX`, `PASSWORD_PATTERN`, `HOST_NAME_MAX`, `ACCOUNT_PASSWORD_MIN`, `CANCEL_MESSAGE_MAX`, the reply's `RSVP_NAME_MAX` / `RSVP_NOTE_MAX` / `RSVP_ANSWER_MAX` / `RSVP_PEOPLE_MAX`: no Zod, so client forms import them without shipping Zod.
- `src/db/paths.ts` — every collection and document path.
- `src/db/secret.ts` — `sign` (HMAC with `FESTIO_SECRET`), `unlockToken`, `unlockMatches`. Dev's secret is a dummy in `.env.development`.
- `src/db/count.ts` — dev only: `countDbUse` counts every Firestore read and write the way Firestore bills them, and session checks; `takeDbCount`. On only with `FESTIO_COUNT_DB=true` on the emulators (the test app copy).
- `src/db/admin.ts` — the Admin SDK (`db`, `auth`). With `NEXT_PUBLIC_USE_EMULATORS=true` (`.env.development`) it talks to the local emulators, ports from `firebase.json`.
- `seed/` — the emulators' seed data and runner: `npm run emulators` starts Firestore, Auth and Storage and seeds them; `npm run seed` resets the data. Host login `maria@festio.test` / `festio-dev`.
- Root: `firebase.json` (emulator ports), `.firebaserc` (`demo-festio`), `firestore.rules` / `storage.rules` (closed until step 6), `firestore.indexes.json`.
